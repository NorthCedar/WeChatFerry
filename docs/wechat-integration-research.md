## 一、调研背景与目标

### 核心需求

- 以个人微信号身份加入群聊，接收并处理群消息
- 支持消息透传到外部 AI 系统，并将回复发回群聊
- 7×24 小时稳定运行，尽可能少的人工干预
- 完整的消息能力（文本、图片、文件、@人等）

### 调研范围

覆盖以下技术路线：

| 技术路线 | 代表方案 |
|---------|---------|
| Web 微信协议 | ItChat、Wechaty、wechatbot-webhook |
| iPad 协议模拟 | GeWeChat (Devo919) |
| 官方 Bot API | weixin-bot-sdk (iLink Bot) |
| Windows PC Hook | WeChatFerry、aixed/WeChat-Hook |
| UI 自动化 | wxauto、wechat-automation-api |
| AI Bot 框架 | LangBot |

## 二、被淘汰方案及原因

在调研过程中，以下 6 个方案经过实际验证后被淘汰。

## 1. ItChat

### 项目简介

ItChat 是一个 Python 编写的微信 Web API 封装库，提供了简洁的 API 来实现微信消息的收发、联系人管理等功能。项目在 GitHub 上获得了大量关注（~25k stars），曾是微信自动化领域最流行的解决方案之一。

### 技术原理

ItChat 基于 Web 微信协议（web.wechat.com）工作。其核心机制为：

- 通过模拟浏览器请求扫码登录网页版微信
- 维持长轮询（Long Polling）获取新消息
- 通过 HTTP 接口调用发送消息、管理联系人等

本质上是对 Web 微信全部 HTTP 接口的 Python 封装。

### 淘汰原因

1. **项目停止维护**：最后一次实质性更新在 2019 年，此后未再适配任何协议变更
2. **Web 微信协议被大面积限制**：腾讯自 2017 年起逐步收紧 Web 微信登录权限，目前大量账号（尤其新注册账号）已无法登录网页版微信
3. **强制掉线问题**：即使能成功登录，Web 协议会在约 2 天后强制断开连接，需要重新扫码登录，无法实现 7×24 小时无人值守运行
4. **协议关闭风险**：微信可能随时全面关闭 Web 协议端，届时所有基于该协议的方案将彻底失效

### 验证过程

通过调研确认：
- 项目 GitHub 页面显示最后活跃时间为 2019 年
- 社区反馈大量"无法登录"问题，作者未回应
- 实际测试目标账号无法登录 web.wechat.com

**结论**：Web 协议本身已不可靠，基于其上的项目无论质量高低均不具备生产可用性。

## 2. Wechaty + wechatbot-webhook (danni-cool)

### 项目简介

Wechaty 是一个跨平台的聊天机器人框架，支持通过不同的 Puppet（协议适配器）接入多种即时通讯平台。wechatbot-webhook（danni-cool/wechatbot-webhook，2.1k stars，MIT 协议）是基于 Wechaty 构建的 Webhook 服务，将微信消息通过 HTTP Webhook 对外暴露。

### 技术原理

- **Wechaty 框架层**：提供统一的 Bot API 抽象
- **Puppet 协议层**：实际使用 `puppet-wechat`（Web 协议）作为底层连接
- **Webhook 层**：将收到的消息通过 HTTP POST 转发到配置的 Webhook URL，同时提供 HTTP API 用于发送消息

架构为：微信 Web 协议 → Wechaty puppet-wechat → wechatbot-webhook → 用户 Webhook 端点。

### 淘汰原因

1. **底层协议限制**：底层仍然使用 Web 微信协议，继承了约 2 天强制掉线的根本问题
2. **项目已归档**：wechatbot-webhook 仓库于 2024 年 12 月被标记为 Archived，不再接受任何更新或 Issue
3. **升级计划未完成**：项目曾规划 v3 版本（基于 Windows Hook）和 Windows 分支，但均未完成即被归档
4. **Wechaty 商业化转向**：Wechaty 的非 Web 协议 Puppet（如 PadLocal、WorkPro）均为付费服务，免费可用的只有 Web 协议 Puppet

### 验证过程

- 确认仓库状态为 Archived（2024-12），README 明确说明不再维护
- 检查 v3 分支和 Windows 分支，均处于未完成状态
- 确认底层 puppet-wechat 使用 Web 协议，存在相同的登录限制和掉线问题

**结论**：即使项目仍在维护，Web 协议的根本限制使其无法满足稳定运行的需求；项目归档更确认了这条路线不可行。

## 3. GeWeChat (Devo919)

### 项目简介

GeWeChat 自称是一个基于 iPad 协议的微信接入方案，通过 Docker 容器部署，对外提供 HTTP API 接口。项目在 GitHub 上发布了 API 文档和 Java 示例代码。

### 技术原理

宣称的架构为：
- Docker 容器内运行核心服务，模拟 iPad 端微信协议进行通信
- 对外暴露 RESTful HTTP API
- 依赖外部"设备库"服务（devicelibrary.cn2.luto.cc）获取设备参数

### 淘汰原因

1. **核心服务从未开源**：仓库中不包含任何核心协议实现代码，仅有 Java API 调用示例
2. **设备库域名失效**：核心依赖的设备库域名 `devicelibrary.cn2.luto.cc` DNS 解析返回 NXDomain，服务不可用
3. **因法律原因停止维护**：作者明确声明因法律风险停止维护

### 验证过程

对仓库进行了深入验证：
- **Git 历史检查**：逐一审查全部 46 个 commit，确认从 initial commit 起仓库仅包含 Java API Demo 代码和文档，从未提交过核心协议服务的源代码
- **DNS 验证**：对 `devicelibrary.cn2.luto.cc` 进行 DNS 查询，返回 NXDomain，表明该域名已不存在
- **Docker 镜像分析**：核心服务以闭源 Docker 镜像形式分发，无法审计安全性

**结论**：这是一个闭源商业服务（以开源名义包装），核心基础设施已下线，完全不可用。即使仍在运行，闭源 + 外部依赖的架构也不满足可审计、可自主部署的要求。

## 4. LangBot

### 项目简介

LangBot 是一个多平台 AI 聊天机器人框架，支持通过适配器（Adapter）接入多种消息平台（QQ、Telegram、微信等），并将消息路由到 AI 大模型进行处理后回复。

### 技术原理

- **适配器架构**：通过 Platform Adapter 抽象层接入不同消息源
- **AI Pipeline**：消息经过 Adapter → Pipeline → AI Provider → 回复
- **插件系统**：支持第三方插件扩展功能

### 淘汰原因

1. **强制绑定 AI Provider**：框架初始化时强制要求配置 AI Provider（如 OpenAI、Anthropic 等）的 API Key，不配置则无法启动。而本项目需求是纯消息转发，不需要 AI 处理
2. **不支持纯转发模式**：框架设计围绕"消息进 → AI 处理 → 回复出"的流程，不原生支持将消息原样转发到外部系统的模式
3. **微信适配器名不副实**：框架中标注的"OpenClaw 微信"适配器实际上仅支持企业微信（WeWork），不支持个人微信

### 验证过程

- 阅读框架文档和配置文件结构，确认 AI Provider 为必填配置项
- 检查消息处理 Pipeline 源码，确认消息必须经过 AI Provider 处理
- 查看微信相关适配器代码和文档，确认仅对接企业微信 API

**结论**：LangBot 的设计目标（AI 聊天机器人）与本项目需求（消息透明转发）存在根本性的架构冲突，强行使用需要大量侵入式修改，不如直接对接消息源。

## 5. weixin-bot-sdk (iLink Bot API)

### 项目简介

weixin-bot-sdk 是基于微信官方 iLink Bot API 的 SDK，是微信官方提供的合规机器人接入方式。Bot 以独立账号形式存在于微信生态中。

### 技术原理

- 基于微信官方开放的 Bot API（iLink 平台）
- Bot 拥有独立身份，通过官方 API 收发消息
- 需要在微信开放平台注册并获取 Bot 凭证

### 淘汰原因

1. **不支持群消息监听**：官方 Bot API 功能受限，无法监听群聊中的所有消息，只能接收 @ 自己的消息
2. **独立身份限制**：Bot 以独立身份存在于微信中，无法以现有个人号身份加入群聊并监听。这意味着需要将 Bot 单独邀请进群，且群成员能看到一个额外的"机器人"账号
3. **与需求不匹配**：本项目需求是将个人号作为消息源进行透传，而非创建一个新的 Bot 身份

### 验证过程

- 查阅 iLink Bot API 官方文档，确认 API 能力范围
- 确认群消息监听不在支持功能列表中
- 验证 Bot 必须以独立身份存在，无法复用现有个人号

**结论**：官方 Bot API 的定位是"企业服务号/客服机器人"，而非"个人号消息桥接"。功能范围与本项目需求不匹配。

## 6. wxauto

### 项目简介

wxauto 是一个 Python 编写的微信自动化工具，通过 Windows UI Automation 接口控制微信 PC 客户端。相比 DLL 注入方案，其优势在于不修改微信进程内存，理论上更安全合规。

### 技术原理

- 基于 Windows UI Automation（UIA）框架
- 通过识别微信窗口中的 UI 元素（按钮、文本框、列表等）进行自动化操作
- 模拟用户点击、输入等交互行为
- 不注入 DLL、不修改进程内存

### 淘汰原因

1. **版本不兼容**：当前环境的微信版本为 4.1.9，该版本 UI 结构发生了重大变化，wxauto 尚未适配，无法正常识别和操作 UI 元素
2. **UI 自动化固有局限**：
   - 依赖 UI 元素的控件名/类名/自动化 ID，微信更新 UI 后容易失效
   - 操作速度受限于 UI 渲染和动画
   - 消息接收依赖轮询窗口内容，存在延迟和遗漏风险

### 验证过程

- 确认当前微信版本为 4.1.9
- 查阅 wxauto 项目文档和 Issue，确认对 4.x 版本的兼容性问题
- 确认项目尚未发布支持 4.1.9 的更新版本

**结论**：版本兼容性问题使其当前不可用。即使未来适配，UI 自动化方案在稳定性和性能上也存在固有劣势，不适合需要长期稳定运行的消息桥接场景。

## 小结

| 方案 | 技术路线 | 核心问题 |
|------|---------|---------|
| ItChat | Web 协议 | 协议受限 + 项目停更 |
| Wechaty + wechatbot-webhook | Web 协议 | 协议受限 + 项目归档 |
| GeWeChat | iPad 协议（闭源） | 从未开源 + 服务下线 |
| LangBot | AI Bot 框架 | 架构不匹配 |
| weixin-bot-sdk | 官方 Bot API | 功能受限 |

上述方案覆盖了微信接入的主要技术路线（Web 协议、iPad 协议、官方 API、UI 自动化、AI 框架），均因各自原因不可行，最终将调研聚焦于 Windows PC 端 DLL 注入 Hook 方案。

## 代码架构分析

### 注入方式

**aixed/WeChat-Hook 的注入方式（C++ 示例）：**

```
DLL_Inject.cpp 流程:
1. CreateToolhelp32Snapshot → 遍历进程找 WeChat.exe PID
2. OpenProcess(PROCESS_ALL_ACCESS) → 打开目标进程
3. VirtualAllocEx → 在目标进程申请内存
4. WriteProcessMemory → 写入 DLL 路径字符串
5. GetProcAddress(Kernel32, "LoadLibraryA") → 获取加载函数地址
6. CreateRemoteThread → 远程线程执行 LoadLibraryA 加载 DLL
```

**与 WeChatFerry 对比：**

| 对比项 | aixed/WeChat-Hook | WeChatFerry |
|--------|-------------------|-------------|
| 注入入口 | CreateRemoteThread + LoadLibraryA | CreateRemoteThread + LoadLibraryW |
| 目标查找 | 进程名遍历 (CreateToolhelp32Snapshot) | 同样的进程快照方式 |
| DLL 卸载 | CreateRemoteThread + FreeLibrary | 类似机制 |
| 本质区别 | **无**（标准 Windows DLL 注入范式） | 同一范式 |

结论：两者的 DLL 注入方式**本质相同**，都是经典的 CreateRemoteThread + LoadLibrary 远程注入。

### 消息收发原理

**aixed 发送消息机制（以 SendText.cpp 为例）：**

```cpp
// 通过偏移量计算目标函数地址
#define SendTextCallOffset 0x6782E7B0 - 0x67370000  // = 0x4BE7B0
DWORD callAddress = GetWeChatWinBase() + SendTextCallOffset;

// 使用内联汇编直接调用 WeChatWin.dll 内部函数
__asm {
    pushad;
    lea eax, wxNull;
    push 0x1;
    push eax;
    mov edi, pWxmsg;
    push edi;
    lea edx, wxWxid;
    lea ecx, buffer;
    call callAddress;   // 直接 call 微信内部函数
    add esp, 0xC;
    lea ecx, buffer;
    call DeleteTextCacheCall;  // 清理缓存
    popad;
}
```

**关键特点：**
- 偏移量硬编码：`目标地址 - DLL基址 = 偏移量`
- 调用方式：内联汇编直接 call，手动构造参数压栈
- 参数传递：通过特定寄存器 (ecx/edx/edi) + 栈
- 版本绑定：偏移量与特定微信版本紧密耦合

**WeChatFerry 发送消息机制：**

```
1. MinHook 框架 → Detour WeChatWin.dll 内部函数
2. 通过 nng (nanomsg-next-gen) RPC 接收外部调用请求
3. 内部使用 function pointer（通过偏移量定位）调用目标函数
4. 使用 nanopb (Protocol Buffers) 序列化参数
```

**对比：**

| 对比项 | aixed/WeChat-Hook | WeChatFerry |
|--------|-------------------|-------------|
| 函数定位 | 基址 + 硬编码偏移量 | 基址 + 硬编码偏移量 |
| 调用方式 | 内联汇编 (__asm) | 函数指针 (C++ 标准调用) |
| 参数传递 | 手动寄存器/栈操作 | 标准 C++ 调用约定 |
| 可移植性 | 仅 x86（内联汇编） | 支持 x86，可扩展 x64 |
| 可读性 | 低（汇编级） | 高（C++ 层面） |

### Hook 技术差异

**aixed/WeChat-Hook — Inline Patch (裸函数跳转)：**

```cpp
// LogMsgInfo.cpp 中的 Hook 实现
DWORD HookLogMsgInfoAddr = GetWeChatWinBase() + HookLogMsgInfoAddrOffset;

// 裸函数，完全手动管理寄存器
__declspec(naked) void doprintmsg(){
    __asm {
        pushad;
        pushfd;
        push eax;          // 原始参数
        call PrintMsg;     // 自定义处理
        add esp, 0x4;
        popfd;
        popad;
        call NextCallAddr; // 调用原始函数
        jmp JmpBackAddr;   // 跳回原位置+5
    }
}

// HookAnyAddress: 将目标地址前5字节改为 jmp 到 doprintmsg
HookAnyAddress(HookLogMsgInfoAddr, (LPVOID)doprintmsg, LogOldAsmCode);
```

**原理：**
1. 保存目标地址原始 5 字节 (`LogOldAsmCode`)
2. 将目标地址 5 字节改写为 `E9 xx xx xx xx` (jmp 相对偏移)
3. 跳转到自定义裸函数，处理后跳回 `目标地址+5`

**WeChatFerry — MinHook Detour：**

```
1. MH_Initialize() → 初始化 MinHook 框架
2. MH_CreateHook(target, detour, &original) → 创建 Trampoline
3. MH_EnableHook(target) → 激活 Hook
4. Trampoline 自动保存/恢复原始指令
```

**对比：**

| 对比项 | Inline Patch (aixed) | MinHook Detour (WCF) |
|--------|---------------------|---------------------|
| 复杂度 | 手动管理所有细节 | 框架自动处理 |
| 安全性 | 需手动保存/恢复寄存器 | 框架保证寄存器安全 |
| 多线程安全 | 需自行处理竞态 | MinHook 内置线程暂停保护 |
| 指令长度处理 | 固定 5 字节覆盖 | 自动计算需覆盖的最小指令数 |
| Trampoline | 无（手动 jmp back） | 自动生成 Trampoline |
| 可维护性 | 低 | 高 |
| x64 支持 | 裸函数不支持 x64 | MinHook 原生支持 x64 |

**关键差异：** aixed 的 inline patch 方式在 x86 环境下可工作，但 `__declspec(naked)` 在 MSVC x64 编译器中不被支持。这意味着 4.x (x64) 版本的 Hook 实现必须使用不同方案（项目主体用易语言实现 x64 Hook）。

### 通信方式

**aixed/WeChat-Hook — HTTP Server：**

```
外部程序 ──HTTP POST──> Hook DLL 内置 HTTP Server ──> 微信内部函数
                                                          │
微信收到消息 ──Hook拦截──> HTTP POST 回调 ──> 外部回调URL
```

- 协议：HTTP REST API
- 数据格式：JSON
- 方向：双向（调用接口 + 消息回调）
- 文档：showdoc.com.cn 在线接口文档
- 配置：启动参数指定回调 URL 和通讯端口

**WeChatFerry — nng RPC：**

```
外部程序 ──nng (pair)──> SDK DLL ──nng (pair)──> spy DLL (进程内)
                                                      │
spy DLL Hook ──nng push──> SDK DLL ──nng push──> 外部程序
```

- 协议：nng (nanomsg-next-gen) pair/push 模式
- 数据格式：nanopb (Protocol Buffers)
- 方向：双向 RPC
- 特点：进程间通信，低延迟，二进制序列化

**对比：**

| 对比项 | HTTP Server (aixed) | nng RPC (WCF) |
|--------|--------------------|--------------| 
| 易用性 | 极高（任何语言 HTTP 调用） | 中等（需 nng 客户端库） |
| 性能 | 中等（HTTP 开销） | 高（二进制 RPC） |
| 跨语言 | 天然跨语言 | 需各语言 nng binding |
| 网络暴露 | 可能暴露本地端口 | 仅本地 IPC |
| 安全性 | 低（HTTP 无认证） | 较高（本地管道） |
| 客户端复杂度 | 极低 | 中等 |

## 可移植性评估

### 核心问题：能否将 aixed 的逆向成果用于 WCF？

**可移植的部分：**

1. **偏移量参考** — aixed 项目持续维护 4.x 版本偏移量，这些偏移量理论上可用于任何 Hook 框架
2. **函数签名** — C++ 示例展示了微信内部函数的参数结构（WxBaseStruct、调用约定等）
3. **数据结构** — 好友列表等内存结构布局可直接参考
4. **功能范围** — 证明了 4.x 版本哪些功能可以通过 Hook 实现

**不可直接移植的部分：**

1. **x86 偏移量** — C++ 示例代码的偏移量为 3.x (x86) 版本，4.x (x64) 的偏移量在易语言主体中
2. **内联汇编** — x86 的 `__asm` 代码无法直接用于 x64（MSVC 不支持 x64 inline asm）
3. **易语言代码** — 主体 4.x Hook 逻辑在易语言中，可读性和可移植性极低
4. **调用约定差异** — x64 使用 fastcall（RCX/RDX/R8/R9），与 x86 的 stdcall/cdecl 完全不同

### 实际可行方案

如果要将 aixed 的成果应用到 WCF：

| 步骤 | 难度 | 说明 |
|------|------|------|
| 1. 提取 4.x 偏移量 | 中 | 需从易语言源码或接口文档中提取 |
| 2. 逆向验证函数签名 | 高 | 需用 IDA/x64dbg 验证 x64 下的参数传递方式 |
| 3. 改用 MinHook x64 | 低 | MinHook 原生支持 x64 Detour |
| 4. 重写调用层 | 高 | x64 fastcall 调用，不能用内联汇编 |
| 5. 适配 nng 通信 | 低 | 通信层与 Hook 层独立 |

### 结论

- **偏移量和功能验证**有参考价值，证明了 4.x 版本可 Hook 的范围
- **代码不可直接移植**，因为 x86→x64 架构差异和易语言壁垒
- **最有价值的是**：证明方案可行 + 提供逆向方向指引 + 接口文档展示了功能边界
- 若要支持 4.x，WCF 需要**独立完成逆向工程**，aixed 的成果仅作为"路标"参考

## 3.2 多维度对比

### 技术原理

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 注入方式 | DLL 注入 (CreateRemoteThread + LoadLibraryA) | DLL 注入 (同左) | 无注入 |
| Hook 机制 | MinHook Detour (函数级 Hook) | Inline Patch (字节级 jmp 跳转) | N/A |
| 通信协议 | nng pair1 RPC + nanopb protobuf | HTTP Server (RESTful) | Flask HTTP Server |
| 消息接收 | 主动推送 (Hook 回调) | 主动推送 (Hook 回调) | UI 轮询 (uiautomation) |
| 架构 | 客户端/服务端分离，protobuf 定义接口 | Hook DLL + 内嵌 HTTP Server | Flask 进程 + UI 自动化脚本 |

**分析：**

- 方案 A 采用 MinHook 框架进行 API Detour，技术成熟度高，调试友好；nng + protobuf 的 RPC 方案性能优秀，序列化开销小。
- 方案 B 使用 inline patch 直接修改目标函数前几字节跳转到自定义处理逻辑，更底层但更脆弱；HTTP 接口降低了客户端接入门槛，任何语言都能直接调用。
- 方案 C 完全规避了逆向工程，通过系统级 UI 自动化 API 操作微信窗口，技术复杂度最低但能力上限也最低。

### 稳定性

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 运行稳定性 | ⭐⭐⭐⭐⭐ 高 | ⭐⭐⭐⭐ 中高 | ⭐⭐ 低 |
| 版本锁定风险 | 低（已锁定，不会被更新破坏） | 中（需跟随微信更新） | 低（不依赖内部结构） |
| 崩溃恢复 | 有成熟的重连机制 | 需自行实现 | 依赖进程监控 |
| 消息丢失率 | 极低 | 低 | 中高（UI 状态异常时丢消息） |

**分析：**

- 方案 A 经过大量用户验证，稳定性最高；但版本锁定意味着无法获得微信新功能。
- 方案 B 作为活跃维护项目，稳定性持续改善中；但微信每次更新都可能导致基址/偏移失效，需要维护者及时适配。
- 方案 C 受 UI 渲染状态、窗口焦点、系统分辨率等因素影响，稳定性最差；长时间运行几乎必然出现异常。

**分析：**

## 4.1 核心结论

经过对六个被淘汰方案和三个入围方案的系统调研，结论如下：

1. **当前没有"完美"的个人微信接入方案。** 每个方案都在稳定性、合规性、功能性之间做出了取舍。
2. **Hook 注入仍是功能最完整的技术路径，** 但面临法律灰色地带和微信版本升级的持续挑战。
3. **微信 3.9.x → 4.x 的架构升级（32位→64位）是分水岭，** 导致生态出现断层：成熟方案不支持新版本，新版本方案尚在成熟中。

1. **版本升级风险：** 微信可能在未来强制升级，导致 3.9.x 无法登录。建议尽早评估方案 B 的可行性。
2. **法律合规风险：** Hook 方案均存在理论法律风险。仅限个人学习研究使用，不建议商业化部署。
3. **封号风险：** 任何非官方接入方式都存在被检测和封号的可能。建议使用非主力账号进行开发测试。
4. **维护成本：** 方案 B 需要持续跟进维护者的更新，建议 Watch 仓库的 Release 和 Issue。

## 4.4 后续行动建议

1. 确定产品需求优先级（稳定性 vs 功能覆盖 vs 版本兼容）
2. 根据场景选择初始方案并搭建 PoC (Proof of Concept)
3. 设计抽象层隔离底层实现，便于未来方案切换
4. 建立版本监控机制，及时感知微信更新和方案适配状态
